# Spring Boot Security Project

## Secure Banking Management System

### Project Objective

Build a secure Banking Management System using Spring Boot and Spring Security.

The application must support multiple users with different roles and permissions.

The main focus of this project is to understand how Spring Security handles:

* Authentication
* Authorization
* Roles
* Authorities
* Permissions
* Password encryption
* Custom UserDetails
* Custom UserDetailsService
* Custom AuthenticationProvider
* SecurityFilterChain
* SecurityContext
* Method-level security
* Authentication exceptions
* Access denied exceptions

---

# Task 13 – Authorities

Convert roles into authorities.

Example:

```text
ADMIN
```

becomes:

```text
ROLE_ADMIN
```

Permissions must be represented as:

```text
ACCOUNT_READ
ACCOUNT_DELETE
TRANSFER_APPROVE
```

A user with ADMIN should therefore have both:

```text
ROLE_ADMIN
ACCOUNT_READ
ACCOUNT_DELETE
TRANSFER_APPROVE
...
```

# Task 14 – Custom UserDetailsService

Create:

`CustomUserDetailsService`

Implement:

`UserDetailsService`

The service must:

1. Receive the email.
2. Search for the customer.
3. Throw `UsernameNotFoundException` if the customer does not exist.
4. Check the customer's status.
5. Convert the customer to `CustomUserDetails`.
6. Return the user.

---

# Task 15 – Custom AuthenticationProvider

Create:

`BankAuthenticationProvider`

Implement:

`AuthenticationProvider`.

The provider must:

1. Read email.
2. Read password.
3. Search for the customer.
4. Validate the customer.
5. Validate the password.
6. Load roles.
7. Load permissions.
8. Create authorities.
9. Return an authenticated token.

---

# Task 16 – Authentication Rules

Authentication must fail when:

* Email does not exist.
* Password is incorrect.
* Customer is disabled.
* Customer account is blocked.
* Customer has no valid role.

Do not return `null` for authentication failures.

Use appropriate Spring Security authentication exceptions.

# Task 21 – Customer Transfer Restriction

A CUSTOMER can create transfers.

However, a CUSTOMER cannot approve transfers.

A CUSTOMER must never be able to call:

`/transfers/{id}/approve`

even if the customer knows the URL.

---

# Task 22 – Transfer Business Rules

Implement the following rules:

### Rule 1

The source account must exist.

### Rule 2

The destination account must exist.

### Rule 3

Both accounts must be ACTIVE.

### Rule 4

Transfer amount must be greater than zero.

### Rule 5

Source and destination accounts cannot be the same.

### Rule 6

Customer cannot transfer more than the available balance.

### Rule 7

A customer can only create a transfer from an account that belongs to them.

---

# Task 23 – Transfer Approval

When a customer creates a transfer:

```text
PENDING
```

The transfer must not immediately move money.

A BANK_MANAGER with:

`TRANSFER_APPROVE`

can approve it.

After approval:

```text
PENDING
      ↓
APPROVED
      ↓
COMPLETED
```

---

# Task 24 – Prevent Unauthorized Approval

A CUSTOMER must not be able to approve a transfer.

An AUDITOR must not be able to approve a transfer.

Only users with:

`TRANSFER_APPROVE`

can approve transfers.

# Task 30 – Ownership Authorization

`GET /accounts/{id}`

For example:

```text

    ↓
```

`/accounts/100`

`403 Forbidden`

# Task 39 – Security Attack Scenarios

Test the application against the following scenarios:

### Scenario 1

A CUSTOMER sends:

`ROLE_ADMIN`

during registration.

The application must reject this.

### Scenario 2

A CUSTOMER changes:

`/accounts/10`

to:

`/accounts/20`

The application must prevent access if account 20 belongs to another customer.

### Scenario 3

A CUSTOMER calls:

`POST /transfers/10/approve`

The request must be rejected.

### Scenario 4

An unauthenticated user calls:

`GET /accounts/10`

The request must be rejected.

### Scenario 5

A user sends another user's email in the request body.

The application must not use that value to bypass ownership checks.
